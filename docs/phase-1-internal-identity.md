# Phase 1 — Internal Identity and Database Foundation

Status: **schema foundation implemented, verification ongoing.**
No application behaviour has been changed: Kite login, the scanner, Live Trade
and every existing route continue to work exactly as before. This phase adds
four new tables only.

This document separates what is **implemented now** from what is **planned**
for later phases. Anything marked *planned* is a design decision, not code that
exists yet.

---

## 1. Purpose and scope

The application is currently single-user: a Zerodha user id doubles as the
owner of everything. Phase 1 introduces a provider-independent internal user
identity so that later phases can add Firebase login, subscriptions and Upstox
without re-keying existing data.

In scope for Phase 1:

- `app_users` — internal DemandScan users (the ownership identifier).
- `user_identities` — provider identity (initially Firebase) → internal user.
- `admin_audit_log` — audit trail for future administrative actions.
- `instrument_aliases` — broker-specific keys mapped onto existing instruments.

Out of scope for Phase 1 (do not start until approved): Firebase login, Upstox
authentication, subscriptions/payments, admin panel, Live Trade data import,
any change to scanner algorithms, any change to `instruments.instrument_id`.

---

## 2. Identity model

### 2.1 Canonical user id

`app_users.user_id` (UUID) is the **only** ownership identifier for
customer-specific records going forward.

- Generated by `gen_random_uuid()`.
- Not derived from email, Firebase UID, Kite user id or Upstox user id.
- Never changes when a user links a new login provider.
- Deleting a user is a deliberate administrative act, not a side effect of an
  identity being removed.

Provider ids never become application ownership ids. This is the key rule that
keeps identity portable across Firebase, Upstox and any future provider.

### 2.2 Columns

| Column | Type | Rules |
|---|---|---|
| `user_id` | `UUID` | primary key, `gen_random_uuid()` |
| `email` | `TEXT` | required, trimmed non-blank, ≤ 320 chars |
| `display_name` | `TEXT` | optional, trimmed length 1–120 |
| `status` | `TEXT` | required, default `ACTIVE`; one of `ACTIVE`, `SUSPENDED`, `DISABLED` |
| `created_at` | `TIMESTAMPTZ` | default `NOW()` |
| `updated_at` | `TIMESTAMPTZ` | default `NOW()`; maintained by application writes |

Email uniqueness is case-insensitive on the trimmed value:

```sql
CREATE UNIQUE INDEX app_users_email_lower_uq ON app_users (lower(btrim(email)));
```

The application must therefore look users up with the same expression
(`lower(btrim(email))`), not with a raw `email = $1`.

**No password column exists and none will be added.** Authentication is
delegated to Firebase; the database never stores a password hash.

### 2.3 Status semantics

- `ACTIVE` — may sign in and use the product.
- `SUSPENDED` — temporarily blocked; data retained. Intended for billing or
  abuse holds.
- `DISABLED` — account closed; data retained for audit and recovery until an
  administrator deliberately deletes it.

Status is checked in the database (`app_users_status_chk`) and must also be
enforced by application middleware on every authenticated request.

## 3. Provider identities (Firebase mapping — planned)

`user_identities` maps an external provider identity to exactly one internal
user. One internal user may have several identities.

| Column | Type | Rules |
|---|---|---|
| `identity_id` | `UUID` | primary key |
| `user_id` | `UUID` | required, FK → `app_users(user_id)` `ON DELETE CASCADE` |
| `provider` | `TEXT` | required; currently only `FIREBASE` accepted |
| `provider_user_id` | `TEXT` | required, trimmed non-blank, ≤ 128 chars |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | defaults `NOW()` |

Uniqueness: `UNIQUE (provider, provider_user_id)` — a given Firebase UID can be
linked to only one internal user. The reverse is not unique: that is why the
user id lives on `app_users` and not here.

`ON DELETE CASCADE` means deleting an internal user removes their identities.
Administrators should normally set `DISABLED` instead of deleting.

### 3.1 Planned Firebase sign-in flow

1. Client signs in with the Firebase SDK and receives an ID token.
2. Server verifies the ID token with the Firebase Admin SDK (not yet installed;
   this is a Phase 2 task).
3. Server reads `firebase_uid` and `email` from the verified token.
4. Look up `user_identities(provider='FIREBASE', provider_user_id=firebase_uid)`.
   - **Found** → load `app_users`, reject unless `status = 'ACTIVE'`.
   - **Not found** → find `app_users` by `lower(btrim(email))`. If found, attach a
     new identity row to it (subject to an explicit linking policy). If not
     found, create `app_users` and the identity in one transaction.
5. Issue the application's own server-side session. The Firebase ID token is
   never used as the application session and is never stored in the database.

Firebase UID is treated as opaque. Expiry, revocation and verification are
Firebase's responsibility; the application trusts only a freshly verified
token.

## 4. Ownership model

### 4.1 What is owned by whom

| Data | Ownership |
|---|---|
| `app_users`, `user_identities` | internal identity |
| Instruments, candles, zones, zone events, coverage/checkpoints | **shared, global** |
| `scan_jobs`, `scan_job_batches` | bound to the browser session that started the scan |
| Live Trade groups/orders (existing) | scoped by `owner_user_id` |
| Future customer-specific data | `app_users.user_id` |

### 4.2 Shared scanner data

Scanner market data is intentionally shared across all users: instruments,
daily and aggregated candles, detected zones, zone events, and ingestion
coverage are facts about the market, not about a customer. Sharing them means
one ingestion and one scan serve every user, which is both cheaper and
consistent.

`scan_jobs` and `scan_job_batches` remain bound to `session_id_hash`
(browser session). Phase 1 does not change this. A later phase may attach an
internal user id to jobs for per-user history, but the execution model stays
browser-driven.

Consequence: no scanner query is filtered by internal user id in Phase 1, and
no scanner table was altered. The Phase 1 integration test re-runs the existing
scanner query shape to prove this.

### 4.3 Future customer-specific tables

Every new customer-owned table must carry `user_id UUID NOT NULL REFERENCES
app_users(user_id)` and scope every SQL statement by it, using a branded type
(similar to the existing `LiveTradeOwnerId`) so that an unscoped query is a
type error rather than a silent data leak.

## 5. Instrument aliases and instrument ID preservation

`instruments.instrument_id` is Kite's numeric instrument token and is the
canonical id across eight dependent tables. It **must not** be renamed,
renumbered, replaced or deleted. Phase 1 preserves it exactly; the integration
test snapshots every row before and after migration and asserts nothing moved.

Upstox identifies instruments with string keys, which cannot be stored in the
existing `BIGINT` column. `instrument_aliases` bridges that:

| Column | Type | Rules |
|---|---|---|
| `alias_id` | `UUID` | primary key |
| `instrument_id` | `BIGINT` | required, FK → `instruments(instrument_id)` `ON DELETE RESTRICT` |
| `provider` | `TEXT` | required; `KITE` or `UPSTOX` |
| `provider_instrument_key` | `TEXT` | required, trimmed non-blank, ≤ 200 chars |
| `exchange` | `TEXT` | required, non-blank, ≤ 32 chars |
| `trading_symbol` | `TEXT` | required, non-blank, ≤ 64 chars |
| `instrument_type` / `segment` | `TEXT` | optional, ≤ 32 chars |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | defaults `NOW()` |

Rules:

- `UNIQUE (provider, provider_instrument_key)` — a broker key identifies one
  instrument within that broker. The same key string under a different provider
  is allowed and unrelated.
- Multiple aliases per instrument are allowed and expected (for example one
  `KITE` row and one `UPSTOX` row for `RELIANCE`). There is deliberately **no**
  unique constraint on `instrument_id` alone.
- `ON DELETE RESTRICT` — an instrument with aliases cannot be deleted by
  accident.
- Indexes: `instrument_id`; `(provider, trading_symbol)` for broker-symbol
  lookups.

Kite tokens and Upstox keys are never compared to each other. Resolution is
always by `(provider, provider_instrument_key)`.

## 6. Administrative audit log

`admin_audit_log` records future administrative operations (suspend user,
change plan, force-disable an account, etc.). It is append-only by convention.

| Column | Type | Rules |
|---|---|---|
| `audit_id` | `UUID` | primary key |
| `actor_user_id` | `UUID` | optional, FK → `app_users(user_id)` `ON DELETE SET NULL` |
| `action` | `TEXT` | required, non-blank, ≤ 80 chars |
| `target_entity_type` | `TEXT` | required, non-blank, ≤ 60 chars |
| `target_entity_id` | `TEXT` | optional, ≤ 200 chars (string form of any id) |
| `metadata` | `JSONB` | required, default `'{}'`, must be a JSON object |
| `created_at` | `TIMESTAMPTZ` | default `NOW()` |

`ON DELETE SET NULL` keeps history if the acting administrator is deleted.
Indexes support recent-first listing, per-actor history, and per-target history.

**Secrets rule:** `metadata` must never contain passwords, access tokens, API
secrets, session ids or full connection strings. The database only guarantees
that it is a JSON object; redaction is enforced in application code. Audit
writes happen in the same transaction as the operation they describe, so an
audit row cannot exist for a change that was rolled back.

## 7. Future Live Trade migration (planned)

Existing Live Trade tables are already scoped by `owner_user_id`, currently the
Kite user id. Phase 1 does **not** change them and imports no data.

When Live Trade becomes multi-user, the planned change is a separate, additive
phase:

1. Add `app_users` rows for existing Live Trade owners (verified mapping).
2. Add a nullable internal `user_id` column to the Live Trade owner table and
   backfill it from the existing owner mapping.
3. Switch reads/writes to the internal user id behind the existing branded
   owner type, keeping `owner_user_id` until the migration is verified.
4. Drop the legacy column only in a later, explicitly approved migration.

Do not backfill by guessing an email. Mapping must be explicit and auditable.

## 8. Subscription expiry model (planned)

Subscriptions and payments are not implemented in Phase 1. The agreed rule for
a later phase:

- A subscription is active through the **end of its paid day in Asia/Kolkata**:
  expiry is `23:59:59.999` IST (UTC `18:29:59.999`).
- There is **no grace period**. At the first instant after expiry the account
  is treated as inactive for paid features.
- Comparisons must use IST explicitly (for example `luxon` `DateTime` with
  `zone: 'Asia/Kolkata'`); never use the server's local timezone.
- Store absolute instants (`TIMESTAMPTZ`) for the expiry value and derive
  display strings in IST.

Access checks must fail closed: if expiry cannot be determined, treat the
subscription as inactive for paid features.

## 9. Future Upstox support (planned)

Phase 1 prepares for Upstox without implementing it:

- `instrument_aliases.provider` already accepts `UPSTOX`.
- `user_identities.provider` is deliberately restricted to `FIREBASE`; adding
  `UPSTOX` requires a future migration that widens the check constraint.
- Upstox OAuth tokens will need their own storage, encrypted like Kite tokens,
  and must never be stored in `app_users` or `user_identities`.
- Upstox instrument keys are strings and resolve only through
  `instrument_aliases (provider='UPSTOX', provider_instrument_key=...)`.

No Upstox code, credentials or auth flow exists today.

## 10. Migration and safety procedure

### 10.1 The migration

File: `db/migrations/2026-11-12-add-internal-identity-foundation.sql`

- Additive and idempotent: every statement is `CREATE ... IF NOT EXISTS`.
- Contains no `ALTER`, `DROP`, `TRUNCATE`, `DELETE`, `UPDATE` or `INSERT`.
- Does not modify any existing table, column, row, index or instrument id.
- Sorts last alphabetically, so the existing runner applies it after all prior
  migrations.

### 10.2 Why a targeted runner exists

`db/migrate.js` always applies `db/schema.sql` plus **every** migration, sorted.
It has no ledger, so running it cannot apply "only the new file". The Phase 1
requirement is to add the new tables without re-running prior migrations and
without risking the configured database. Therefore Phase 1 adds:

`db/migrate-phase1.js` (`npm run db:phase1:migrate`)

Safety properties:

- Reads **only** `PHASE1_DATABASE_URL`; never falls back to `DATABASE_URL` or
  `.env.local`.
- Requires `ALLOW_PHASE1_MIGRATION=YES` and `EXPECTED_PHASE1_HOST`.
- Refuses when `NODE_ENV=production`, when the host is on `FORBIDDEN_DATABASE_HOST`,
  when the URL is not Neon, or when the URL is pooled (`-pooler`).
- Reads only the one Phase 1 migration file.
- Refuses any statement that does not start with `CREATE`.
- Verifies the four tables exist after applying.
- Prints only sanitized host/database metadata, never credentials.

It has not been run against any real Neon database, including the configured
development database.

### 10.3 Reapplication

All `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` statements make
a second run a no-op. Reapplication is covered by the integration test, which
applies the migration twice to a disposable database and asserts the instrument
snapshot is unchanged.

### 10.4 Recommended production procedure (later, explicit approval only)

When Phase 1 is approved for a real environment, apply only this file:

```bash
PHASE1_DATABASE_URL="postgres://...direct-neon..." \
EXPECTED_PHASE1_HOST="ep-<id>.<region>.aws.neon.tech" \
ALLOW_PHASE1_MIGRATION=YES \
npm run db:phase1:migrate
```

Then verify read-only with the existing check (now aware of the four new
tables):

```bash
npm run db:verify
```

Do not use `npm run db:migrate` for this step.

## 11. Verification

Static contract tests: `__tests__/identity/phase1-schema.test.ts`

- migration exists and sorts last;
- creates exactly the four tables;
- every statement is `CREATE ... IF NOT EXISTS`;
- no destructive DDL/DML keywords;
- required columns, keys, checks, indexes and foreign keys;
- `instruments` is never altered.

Database integration tests: `tests/phase1/identity-schema.integration.test.ts`

- skipped unless `PHASE1_TEST_DATABASE_URL` points at a disposable database;
- applies the pre-Phase-1 schema and migrations, seeds sentinel instruments,
  snapshot them, then applies Phase 1 twice;
- asserts instrument ids are byte-for-byte unchanged;
- user creation/defaults, case-insensitive + trimmed email uniqueness, status
  values;
- Firebase UID uniqueness and identity → user mapping;
- FK enforcement and cascades;
- audit row creation, JSONB object requirement, nullable actor;
- KITE + UPSTOX aliases on one instrument, duplicate provider key rejection;
- `EXPECTED_SCHEMA` is fully present and the existing scanner query still runs.
